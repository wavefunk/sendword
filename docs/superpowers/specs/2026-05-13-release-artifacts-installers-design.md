# Release Artifacts And Installers Design Spec

## Motivation

`sendword` needs prebuilt GitHub Release artifacts and one-line installers in
the style common Rust CLI projects use:

```sh
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/wavefunk/sendword/releases/latest/download/sendword-installer.sh | sh
```

Windows users need the PowerShell equivalent. This task adds the GitHub release
artifact and installer pipeline. It does not publish Docker images and does not
change runtime JavaScript/Python script support.

## Approach

Use `cargo-dist` rather than hand-written release packaging. The repo already
includes `cargo-dist` in the Nix development shell, and `dist` is designed to
generate GitHub release workflows, archives, checksums, shell installers, and
PowerShell installers from Cargo metadata.

The workflow is generated by `dist generate --mode=ci`. Hand-editing the
generated release workflow is avoided because `dist` treats the workflow as
generated output and can regenerate it when configuration changes.

## Release Scope

The initial release artifact matrix is intentionally narrow:

- `x86_64-unknown-linux-gnu`
- `x86_64-pc-windows-msvc`

Installers:

- `shell`: produces the Unix `curl | sh` installer.
- `powershell`: produces the Windows `irm | iex` installer.

The installer destination is `CARGO_HOME`, matching `cargo install` behavior.

## Files

`Cargo.toml` gains a `dist` profile:

```toml
[profile.dist]
inherits = "release"
lto = "thin"
```

`dist-workspace.toml` contains the cargo-dist workspace config:

```toml
[workspace]
members = ["cargo:."]

[dist]
cargo-dist-version = "0.30.4"
ci = "github"
installers = ["shell", "powershell"]
targets = ["x86_64-unknown-linux-gnu", "x86_64-pc-windows-msvc"]
install-path = "CARGO_HOME"
install-updater = false
```

`.github/workflows/release.yml` is generated by:

```sh
nix develop -c dist generate --mode=ci
```

`docs/release/github-release.md` documents the release flow and the user-facing
install commands.

## Triggering

The generated Release workflow runs on version tags such as `v0.0.2`. It may
also include a pull-request planning trigger generated by cargo-dist; that is
acceptable because it only checks release planning and helps catch broken release
configuration before a tag is pushed.

The crates.io publish workflow from the previous task also runs on `v*.*.*`
tags. Both workflows are expected to run for the same version tag: one publishes
the crate, the other builds and hosts release artifacts.

## Validation

Local validation uses cargo-dist directly:

- `nix develop -c dist plan --tag v0.0.2 --output-format=json`
- `nix shell nixpkgs#actionlint -c actionlint .github/workflows/release.yml`
- `git diff --check`

The `dist plan` output must include the two configured targets and the shell and
PowerShell installers. The full cross-platform builds run in GitHub Actions when
a release tag is pushed.
